## Encrypted database capture and fenced restore

`npm run recovery:database -- --plan` is inert. Capture requires `--capture --allow-hosted-capture --manifest=<reviewed-manifest> --output=<new-private-file>`; restoration requires `--restore --allow-fenced-restore --manifest=<reviewed-manifest> --archive=<private-file> --image=sha256:<cached-image-id>`. Both require private stdin and fresh target/action/binding authorization, valid for at most 24 hours. The command has no inferred/default action, source reset, hosted destination, access-enable operation or image-pull fallback.

| Input | Capture | Fenced restore |
|---|---|---|
| Backup key | `backupKeyB64`, `keyId`: separately retained 32-byte key; never part of the archive | Same retained key/version |
| Trace keys | `traces: {activeId, keys: {keyId: base64}}`, at most ten versions | All versions needed by the archive's actual encrypted samples |
| Connection | `connection: {host, port: 5432, user, password, caCertificatePem}` | No source connection or password |
| Authorization | Purpose `synthetic-database-capture`, exact target hash, `bindingSHA256` from `databaseCaptureBinding(connectionIdentity(...), output)`, expiry and `approved: true`; explicit `independentBackupCustody` and `separateKeyCustody` attestations | Purpose `synthetic-fenced-database-restore`, exact target hash, binding from `databaseRestoreBinding(archive, image)`, expiry and `approved: true` |

Capture accepts only the manifest's direct database identity or its region-bound session pooler identity. Port 6543, arbitrary hosts, different projects/regions and incomplete CA input are refused. The approval binding includes host/user/database, verified-TLS mode, CA certificate SHA-256 and resolved output path. The database password enters only the child process environment, never arguments or persistent container configuration. The public CA travels through stdin to a temporary client-container file that is removed on shell exit. `sslmode=verify-full` verifies both host and certificate; there is no `require`/disabled-verification fallback. Source SQL uses read-only transactions and a read-only session default.

The existing local PostgreSQL client container runs `pg_dump` for only `public`, `auth`, `storage` and `supabase_migrations`, preserving their ownership/grants. Default CLI schema export excludes Auth, so this path deliberately uses a bounded custom archive and strict full-schema comparison rather than assuming the filtered default is complete. The grouped rehearsal verified managed source privileges and compatibility with the recorded isolated service images; other sources/versions are unverified. Unknown owners, unsupported extensions or restore errors stop the run; do not remove objects/rows/grants to force compatibility.

Source snapshots before and after dumping compare logical schema/functions/triggers/policies/grants/RLS/owners, extension versions, every selected table's count/hash and one encrypted sample per present trace-key version. All 19 current public tables and Auth users must appear. Real identities, Storage objects, missing keys, changing source state and dumps over 128 MiB are refused. Samples must actually decrypt. A changed source produces no completed archive; concurrent changes that evade the before/after checks still cannot pass a later restore unless its rows match the authenticated inventory. The outer AES-256-GCM archive authenticates the source binding, snapshot and dump, with the existing 30-day ceiling. Raw dump bytes remain in memory; the exclusive-created, flushed output contains ciphertext only.

Restore authenticates the entire archive, source and retained trace keys before creating its destination. It creates a fresh UUID-named container from an explicitly pinned cached image with `--pull=never --network=none`; it publishes no ports and mounts no host paths. Ordinary restore runs no Auth/API service; explicitly approved HTTP verification shares only this isolated network namespace. Only an empty destination is eligible: image-initialized empty Auth tables/system migration metadata are allowed; product tables or user rows are refused. The operator does not select an existing destination. Restoring into the four fresh schemas is transactional and stops at the first error. The owned immutable container ID is used for operations and cleanup; it stops on success/failure and leaves its volume for operator inspection. A failed stop remains an error requiring inspection.

Restored rows/catalog/extensions/trace samples must match the authenticated source snapshot. Comparison normalizes only physical attribute positions, ACL ordering, equivalent CHECK parse trees and database-catalog names. Source reads never create temporary tables; CHECK definitions are reparsed only inside the fenced destination. Table/schema/column identity, logical types, constraints, owners, grantors/grantees/privileges, policies and row contents remain checked. The result always says `restoreAccessAuthorized: false` and names the remaining journal replay, session revocation and Auth/API gates. A stopped restored volume contains a decrypted database, including synthetic Auth records; it requires the approved private machine/storage even though the backup file stays encrypted.

The existing local-only `backup:verify` retains its source guards and procedure. Shared comparison SQL is extracted without changing its original queries. [3D.4B evidence](../evidence/owner-pilot-step3d4-database.md) records actual interfaces, failed attempts and proof limits.

### Fenced journal replay and recovery validation

`recovery:database --recover` adds reconciliation to the same authenticated restore. It requires `--allow-fenced-restore --allow-hosted-journal-read --manifest=<reviewed-manifest> --archive=<private-backup> --image=<pinned-image> --journal=<independent-initial-copy> --journal-latest=<new-private-file>`. It is distinct from `--restore`: no journal source request is inferred from an ordinary restore. There is still no access-enable operation. Auth/API checks require the additional explicit HTTP mode described below.

Private stdin extends the restore input with `journal`, using the existing journal-capture input schema (key/version, Management token and exact target/output/expiry/custody authorization). The outer purpose is `synthetic-fenced-database-recovery`; its binding is `databaseRecoveryBinding(archive, image, initialJournal, latestPath)`, covering the archive/image, authenticated initial copy and latest output path. The nested capture authorization separately binds the latest path/source. Both approvals can come from one reviewed owner-approved rehearsal; individual continuation/read confirmations are unnecessary inside that scope.

The initial journal must authenticate for the backup source/time and be current before creating the destination and again before replay. More than 100 records or explicitly unresolved source accounting is refused. Replay performs at most 100 continuations per record and 1,000 total, using existing deletion functions and batches of 100. It never shortens holds, resets allocations or guesses completion. A restored unfinished request absent from the independent journal, mismatched receipt identity, phase regression, unconfirmed Auth removal, future accounting hold or limit leaves recovery blocked.

Replay acts only on journal-authorized identities in the fresh destination. It preserves the original receipt identity/request time, replays existing product deletion/fencing, removes Auth only after the application reaches `auth_removal_pending`, and independently checks all 16 owned table categories and Auth absence. Completed source timestamps are retained. Accounts absent from the older archive still need verified absence and a completion record. The code never creates a deletion request on the hosted source.

Before/after hashes protect unaffected owners' rows/Auth data, global route-cost blocks and Vertex approval records. Shared app buckets retain their identity/allocation/metadata, cannot lose spent charges or acquire negative reservations, and may settle only through existing deletion accounting. Monetary comparisons use exact decimal strings and Decimal, including sub-double-precision changes. These replay checks preserve the archive accounting. Recovery additionally compares its final ledger fingerprint with the current independent source snapshot; divergence blocks recovery rather than resetting balances or reconstructing spending.

All old session identities are recorded before replay, including sessions later removed with deleted accounts. Remaining refresh/session rows are deleted globally only inside the new destination. Validation proves zero persisted sessions/tokens and tests every recorded old session against the database's actual live-session predicate. For up to two remaining active profiles, fresh probe sessions exist only in rolled-back transactions: authenticated role checks must see the owned profile, no foreign profiles/conversations, and no direct private-payload grant. A single/empty remaining account set does not claim two-owner proof; the report states the count and `twoOwnerRlsVerified`. This is SQL-policy proof; the additional HTTP mode below tests actual GoTrue/PostgREST behavior.

Only after replay/revocation/validation does recovery make one explicitly approved read-only Management API journal capture. The new copy is encrypted and create-only in the approved independent location. Its authenticated rows must exactly match the initial journal, including unfinished phases and timestamps. The same source statement fingerprints app/account buckets, reservations, verification allocations, runs/steps, global cost blocks and Vertex policy. Rows owned by journal-authorized deleted identities are excluded on both sides; shared app rows and every unaffected owner remain included. The restored final fingerprint must match the current source exactly. Missing accounting evidence or any drift blocks recovery; old journal copies remain readable by standalone verification but cannot complete recovery. Failure, a changed record, stale copy, wrong source/key or an existing latest output stops the operation; evidence is retained and access stays blocked. No source mutation, account discovery for hosted deletion or silent retry occurs.

The owned container remains network-isolated and stops on success/failure. Every result says `restoreAccessAuthorized: false`. A fresh unchanged reread is not an atomic source fence and cannot establish completeness after unobserved source loss. The bounded managed-source privileges/TLS/schema/Auth/API path passed; key/cloud-copy readbacks passed; actual cutover/source-loss coverage and ongoing custody/rotation retain their separate requirements. PR #32 consolidates the remaining preparation and ensuing approved rehearsal evidence; no additional preparation PR is planned. [3D.4C evidence](../evidence/owner-pilot-step3d4-replay.md) owns observed results and failures.

The recovery binding includes image IDs and identity IDs/emails, never passwords. The CLI refuses a flag/input mismatch. Credentials enter through private stdin and are never reset by this verification.

The two fresh service containers share the owned database container's **network-none namespace**. They listen only on its loopback interfaces, publish no host ports, use no mounts, pull no images and have no outbound network. The operator verifies their immutable IDs, image/namespace/mount/port fence before starting them. New Auth/database role secrets exist only inside this disposable destination and service containers; both services are removed after success/failure. Source credentials/configuration are unchanged.

Actual HTTP checks cover preserved-password sign-in, deleted-user sign-in denial, owned profile/conversation reads, foreign profile denial, direct private-payload denial, global logout, database live-session rejection of old JWTs, refresh-token rejection, anonymous denial and exact `signup_disabled` errors. ## Independent deletion journal

`npm run recovery:journal -- --plan` is inert: no credentials, file reads or network. Capture requires all of `--capture --allow-hosted --manifest=<reviewed-manifest> --output=<new-private-file>`. There is no default capture, scheduler, owner discovery, source mutation, database backup or restore endpoint.

The private stdin JSON contains the existing Management API `accessToken`, a separate 32-byte `journalKeyB64`, its `keyId`, and `authorization`. The authorization requires purpose `synthetic-recovery-journal-capture`, exact `targetSHA256`, `outputPathSHA256` (SHA-256 of the resolved absolute output path through `recoveryPathHash`), an expiry within 24 hours, and explicit `approved`, `independentJournalCustody` and `separateKeyCustody` attestations. These bind the selected target/output and operator approval; they do not independently prove storage durability or key custody. Extra input fields are rejected. Load credentials privately from protected files into stdin; never put values in arguments, chat, screenshots, Git or public environment variables.

Capture sends exactly one fixed Management API query to the manifest source, with `read_only: true`, redirects/cookies disabled and a 25-second deadline. One PostgreSQL statement returns database time, the complete deletion journal including unfinished requests, a SHA-256 accounting fingerprint and synthetic-identity/empty-Storage counts. Counts must agree with returned records; more than 10,000 receipts or 5 MiB, duplicate identities/receipt IDs, invalid lifecycle timestamps, real/phone-only identities or Storage objects stop capture. There is no pagination gap or silent truncation. The command never reads health rows, prompts, password hashes or tokens from Auth.

The source clock must be within five seconds ahead and less than five minutes behind the operator clock. Encryption reuses the existing AES-256-GCM archive format with target identity and journal contents inside the authenticated ciphertext. Output uses exclusive creation and flushes the file before reporting success. Existing files and aliased parent directories are refused; directories must already exist. A write failure can leave an incomplete ciphertext file: preserve it for inspection and select a new approved filename rather than overwriting it. Key/plaintext byte buffers are cleared after sealing. Reports contain counts/hash/mode, never account IDs, receipt bodies, paths or secrets.

Offline verification uses `--verify --manifest=<reviewed-manifest> --archive=<private-file>`, without `--allow-hosted`. Private stdin contains only `keyId`, `journalKeyB64` and `backupCreatedAt`. The eventual restore caller must obtain that timestamp from the authenticated backup header; typing an arbitrary timestamp into this standalone check does not establish backup validity. It authenticates before exposing replay records, checks source binding, complete row/lifecycle structure, backup-time coverage and freshness. The CLI prints only the safe report. Missing/wrong keys, corruption, old/pre-backup records and a different source fail closed. Unfinished requests remain replay obligations, not records to omit.

Every result says `restoreAccessAuthorized: false`. A fresh snapshot does not prove that all later source changes have been captured. Before access, the restore procedure must establish current independent completeness, replay every applicable deletion, reconcile again, revoke restored sessions and keep the destination fenced until separately approved.

The five-minute archive validity is an acceptance window for a current recovery check, not permission to delete older independent records. Keep retained records and their keys under the approved custody/rotation policy. After source loss, an old copy alone cannot prove there were no later deletions; missing current completeness evidence must leave access blocked. A source-loss coverage/cutover procedure remains part of 3D.4B/C.
