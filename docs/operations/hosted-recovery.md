# Hosted-source recovery

Step 3D.4 prepares recovery of the approved synthetic Supabase source into a separate fenced destination. No hosted backup/journal capture or restore has been approved or executed. The owner is the manual maintenance operator. [Release readiness](release-readiness.md) owns pilot gates; [account lifecycle](account-lifecycle.md) owns deletion/retention semantics.

## Checkpoints

| Checkpoint | Current behavior | Remaining gate |
|---|---|---|
| 3D.4A independent journal | `recovery:journal` captures a complete, source-bound encrypted deletion snapshot; validates it offline against a supplied authenticated backup time | Prepared and locally verified. Include exact capture/output/custody in the eventual recovery execution approval |

| 3D.4C fenced restoration | Existing local-source rehearsal does not establish hosted compatibility | Prove an empty separate destination, block Auth/API access before restore, replay the current independent journal, settle uncertainty without resets, revoke restored sessions and verify failure cases; separate access approval |

Supabase's [platform-to-self-hosted procedure](https://supabase.com/docs/guides/self-hosting/restore-from-platform) uses its filtered CLI roles/schema/data exports and calls out Auth/PostgreSQL compatibility differences. This supports investigating the local destination; it does not prove Vulpes recovery. Do not drop unknown Auth rows/columns, omit grants or skip restore failures. No source overwrite, unrelated-project access, paid upgrade or provider activation is included.

## Independent deletion journal

`npm run recovery:journal -- --plan` is inert: no credentials, file reads or network. Capture requires all of `--capture --allow-hosted --manifest=<reviewed-manifest> --output=<new-private-file>`. There is no default capture, scheduler, owner discovery, source mutation, database backup or restore endpoint.

The private stdin JSON contains the existing Management API `accessToken`, a separate 32-byte `journalKeyB64`, its `keyId`, and `authorization`. The authorization requires purpose `synthetic-recovery-journal-capture`, exact `targetSHA256`, `outputPathSHA256` (SHA-256 of the resolved absolute output path through `recoveryPathHash`), an expiry within 24 hours, and explicit `approved`, `independentJournalCustody` and `separateKeyCustody` attestations. These bind the selected target/output and operator approval; they do not independently prove storage durability or key custody. Extra input fields are rejected. Load credentials privately from protected files into stdin; never put values in arguments, chat, screenshots, Git or public environment variables.

Capture sends exactly one fixed Management API query to the manifest source, with `read_only: true`, redirects/cookies disabled and a 25-second deadline. One PostgreSQL statement returns database time, the complete deletion journal including unfinished requests, and synthetic-identity/empty-Storage counts. Counts must agree with returned records; more than 10,000 receipts or 5 MiB, duplicate identities/receipt IDs, invalid lifecycle timestamps, real/phone-only identities or Storage objects stop capture. There is no pagination gap or silent truncation. The command never reads health rows, prompts, password hashes or tokens from Auth.

The source clock must be within five seconds ahead and less than five minutes behind the operator clock. Encryption reuses the existing AES-256-GCM archive format with target identity and journal contents inside the authenticated ciphertext. Output uses exclusive creation and flushes the file before reporting success. Existing files and aliased parent directories are refused; directories must already exist. A write failure can leave an incomplete ciphertext file: preserve it for inspection and select a new approved filename rather than overwriting it. Key/plaintext byte buffers are cleared after sealing. Reports contain counts/hash/mode, never account IDs, receipt bodies, paths or secrets.

Offline verification uses `--verify --manifest=<reviewed-manifest> --archive=<private-file>`, without `--allow-hosted`. Private stdin contains only `keyId`, `journalKeyB64` and `backupCreatedAt`. The eventual restore caller must obtain that timestamp from the authenticated backup header; typing an arbitrary timestamp into this standalone check does not establish backup validity. It authenticates before exposing replay records, checks source binding, complete row/lifecycle structure, backup-time coverage and freshness. The CLI prints only the safe report. Missing/wrong keys, corruption, old/pre-backup records and a different source fail closed. Unfinished requests remain replay obligations, not records to omit.

Every result says `restoreAccessAuthorized: false`. A fresh snapshot does not prove that all later source changes have been captured. Before access, the restore procedure must establish current independent completeness, replay every applicable deletion, reconcile again, revoke restored sessions and keep the destination fenced until separately approved.

The five-minute archive validity is an acceptance window for a current recovery check, not permission to delete older independent records. Keep retained records and their keys under the approved custody/rotation policy. After source loss, an old copy alone cannot prove there were no later deletions; missing current completeness evidence must leave access blocked. A source-loss coverage/cutover procedure remains part of 3D.4B/C.

Do not request an isolated hosted capture merely to finish this preparation packet: its current-check window would expire before the remaining recovery implementation is ready. Continue ordinary database capture/restore preparation independently, then group the concrete custody, source-read and fenced-destination actions into a reviewable execution approval. Fresh journal captures within that approved rehearsal use the same approved scope rather than separate confirmation for each read.

## Owner custody setup before hosted capture

No new provider dashboard or database-password entry is needed for journal capture: the existing scoped Supabase Management token suffices. Full database capture may need a separately protected connection credential once its supported path is implemented. Do not reset a database password or widen the token's scope speculatively.

The concrete owner checkpoint is choosing private locations and retaining the recovery key independently of this checkout and source:

1. Choose a private folder on your computer for encrypted journal copies. Avoid the repository, shared/public folders and any location that other people can edit. This keeps the copy independent of the hosted source; a copy on the same computer is still vulnerable to losing that computer. Confirm the intended folder and a second recovery location you already control, if available. No new storage service or payment is required by this packet.
2. Choose a separate existing password manager or other owner-controlled protected key store. Enable its account MFA where supported. Create an entry named **Vulpes recovery journal key**. Do not store the only key beside the encrypted journal, in this chat, or solely in Windows DPAPI on this computer; that would prevent recovery after losing the computer/account. Password-manager fees or new external services require separate approval.
3. Report only the folder location(s), which key store you will use and whether MFA is enabled. Do not send keys or passwords. When the remaining capture/restore implementation is ready, the execution approval must identify the specific synthetic source, private outputs, fenced disposable destination, actions and $0 paid allowance. Journal-only approval does not imply a full backup/restore; a reviewed combined rehearsal can approve both together. No scheduler or restored access is implicit.
4. After that approval, the agent prepares a fresh journal key in protected local storage and supplies private-terminal instructions to place it in your chosen store and verify a readback. The key must not be printed through agent tools. Hosted capture waits until that custody check is confirmed; the command's attestation fields are not a substitute for the check.
5. The agent captures and validates the encrypted file, records safe counts and verifies its independently stored copy. Report whether you can find the key entry and encrypted file in the agreed locations. Never paste their contents into chat. Do not infer restore readiness from this capture.

The tool is prepared for this bounded action; no key has been generated or copied into an external store during preparation. Complete database recovery still needs the later compatible capture/fence/replay checkpoints. The original accounts, completed rehearsal artifacts and retained Luna allocations remain untouched.
