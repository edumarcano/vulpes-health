# Vulpes v0.2.0 release implementation plan

**Status:** M0 decision/feasibility packet complete with documented M2/M3 evidence gates; M1-M6 implementation and runtime release acceptance remain pending.

**Date:** 2026-11-11

**Inspected revision:** `3b7e5762c732ebddf892068635fbe575a33a0f45` (`docs/0.2.0-specs`).

**Requirements:** [Vulpes v0.2.0 specification](spec/v0.2.0/VULPES_V0.2.0_SPEC.md).

## 1. Release outcome and authority

Deliver Vulpes body-composition history and analysis with supported RENPHO Health CSV imports: select or share an export, review and confirm an accurate import, explore event-linked metrics and historical periods, ask grounded questions, approve individual or grouped goals, and safely import overlapping history. Data, references, and goal progress must work with inference disabled.

Preserve specification milestones **M0–M6**. Repository inspection supports their boundaries; no compelling reason to replace or renumber them was found. This plan sets dependencies, architectural direction, and acceptance gates. Each milestone receives its own scoped implementation plan before work begins; this document does not prescribe individual patches or PRs.

The v0.2.0 specification supersedes conflicting v0.1.0 scope, RENPHO, compatibility, and model-selection requirements. The unchanged [architecture](spec/v0.1.0/ARCHITECTURE.md), [data semantics](spec/v0.1.0/DATA_MODEL.md), [API](spec/v0.1.0/API_CONTRACTS.md), [AI controls](spec/v0.1.0/AI_SPEC.md), [security and privacy](spec/v0.1.0/SECURITY_AND_PRIVACY.md), and [MOD-01–06 acceptance requirements](spec/v0.1.0/ACCEPTANCE_TESTS.md) remain constraints. Follow [AGENTS.md](../AGENTS.md) and the engineering, testing, and documentation standards under `.remora/standards/`.

Keep Ask | Goals | Data | Settings, existing branding, shadcn/ui, assistant-ui, and the TypeScript modular monolith. Retain inexpensive manual and canonical CSV paths. Native packaging, health-platform synchronization, generic vendor ingestion, autonomous coaching, external-agent endpoints, decision scoring, and the full Issue #35 benchmarking platform remain deferred.

Planning does not authorize deployment, destructive resets, real-data imports, paid evaluations, model activation, or consequential user actions. These require their applicable later approvals. Historical owner-pilot exceptions and technical model evidence do not satisfy v0.2.0 acceptance.

## 3. Architectural direction and decision gates

These are release planning recommendations. Proposed mechanisms are not mandatory when a simpler approach satisfies the same specification contracts, acceptance criteria, and architectural safeguards. M0 records the material trade-offs needed to begin implementation in [implementation decisions](DECISIONS_IMPLEMENTATION.md); later choices are resolved and recorded by their owning milestones at the closure gates below. Routine naming and file layout belong to milestone planning.

Reuse existing services, abstractions, and test infrastructure wherever appropriate. Add abstractions or infrastructure only for demonstrated v0.2.0 needs; do not introduce general-purpose frameworks or infrastructure solely for hypothetical future requirements.

| Decision | Recommended direction and rationale | Closure gate |
|---|---|---|
| Schema strategy | Prefer forward migrations extending the existing schema, with an explicit owner-scoped weigh-in parent or equivalent reliable event linkage in the existing model. This preserves mature authentication, accounting, RLS, and lifecycle infrastructure. No dual readers or backfills solely for disposable v0.1.0 history. | M0 compares this with a fresh application-data baseline, inventories affected data classes, and selects the simpler reproducible route before M1 schema work. Applied migrations are not casually rewritten. |
| Source and event identity | Extend owned source contexts with confirmed profile assumption, adapter/layout version, and import timezone defaults. Define event identity from source/time and tested equality rules, separate from observation identity. Different timestamps stay distinct; same-time ambiguity remains a conflict. | M0 fixes identity, normalization equivalence, and timezone-change policy; M1 proves overlap, enrichment, conflict, and correction behavior. Row numbers, filenames, proximity, and raw hashes cannot define identity alone. |
| Metric semantics | Consolidate a small typed, versioned registry for all 19 core and five optional numeric fields, retaining original values/units and source limitations. Keep categorical annotations separate. Reconcile SQL and runtime validation explicitly. | M1 proves parity across ingress, storage, and projections. Unresolved semantics remain preserved and visible but ineligible for analytical/goal operands. No invented units, physiological formulas, or fuzzy unit equivalence. |
| Import staging and commit | Share mapping/source metadata at batch/event level; keep normalized staging encrypted and bounded. Prefer one transaction if measured capacity allows. If internal chunking is necessary, incomplete stages remain invisible and final publication is atomic. | M1 demonstrates 1,000 fully populated weigh-ins through the real preview/commit path, plus boundary, concurrency, lost-response, and rollback tests. Measure bytes and latency before changing payload or hosting limits. |
| Analytical results | Reuse exact arithmetic behind explicit latest-event, latest-per-metric, selected-period, rolling, and comparison operations. UI and AI share server-issued result identities, methods, revisions, coverage, and evidence. | M3 settles result/version contracts and cache identity, including owner/source/timezone/method/data revision. Historical evidence is retained truthfully or unavailable, never silently recomputed as the original. |
| Share handoff | Prefer a service-worker POST receiver and isolated browser-local store, with opaque references, a single consumer, and at most 15 minutes' validity. Continue through the same authenticated preview as file selection. | M0 tests feasibility; M2 proves sign-in continuity, account binding, expiry, races, worker/network failure, and actual Android sharing. No shared health cache, anonymous ingest write, or background commit. |
| References | Use reviewed versioned definitions and a bounded deterministic reference registry. Collect only profile attributes needed by verified applicable rules; allow refusal. | M0 investigates sources/applicability. M3 records per-metric coverage and proves at least one verified applicable rule, or records the evidence blocker. Universal range coverage is not required. |
| Goals and groups | Generalize existing definitions and approval services. Groups hold up to four owned goals with independent baselines and all-members semantics. Prefer atomic approval of the reviewed group; use explicit separate member approvals only if justified and clearly presented. | M4 resolves the approval transaction boundary and proves no partial activation reported as complete, no score averaging, and correct invalidation on member changes. |
| AI configuration | Keep current routing unavailable where unverified; compare the everyday baseline against peers after contracts stabilize. Prefer one model with fixed effort. Keep candidates separate from production availability and parameters centralized in `server/config/models.ts`. | M5 selects from current capability/privacy/price and full-task quality evidence. Adaptive effort or one bounded handoff needs demonstrated benefit and fresh consent/accounting evidence; neither is assumed. |

Source local time, resolved instant, and display timezone are different concepts. Saved preferences must not reinterpret old imports. Likewise, import recency must not masquerade as measurement freshness, and a manufacturer's reference or “optimal” value must not become an approved goal.

## 4. Milestone dependencies and implementation order

The default delivery order is **M0 → M1 → M2 → M3 → M4 → M5 → M6**. The hard product dependency is **M0 → M1 → M3 → M4 → M5 → M6**, with **M1 → M2 → M6** providing the ingestion/device branch. M2 does not require completed analytics; M3 does not require the share receiver. If device access blocks M2 evidence, M3–M4 may proceed against the file picker while the M2 gate remains explicitly open.

Start share feasibility, reference investigation, and evaluation design in M0. Run offline regressions throughout. Bring isolation, export/deletion, and compatibility protection into each owning milestone; M6 verifies the integrated release rather than discovering these obligations for the first time. UI changes accompany their domain capabilities and receive final cross-application review in M6.

### M0 — Reconcile and de-risk

**Depends on:** This plan and the authoritative specification; repeat the bounded revision comparison if implementation starts at another revision.

Resolve only the decisions needed to safely begin subsequent implementation. Keep investigation and feasibility checks bounded; detailed feature design and implementation belong to the owning milestones, with the dependencies and exit gates below unchanged.

Map affected contracts and choose schema/cutover direction. Confirm the supported English CSV dialect, verified mass aliases, ambiguous-field handling, and source/event identity rules. Investigate manufacturer applicability and obtain synthetic format evidence. Perform the smallest nonproduction share-receiving feasibility check, including the actual export MIME behavior where device access permits. Define the comparison cases, scoring, candidate-selection rules, and later approval needs without paid calls.

**Exit:** The [M0 readiness record](evidence/v0.2.0/m0-readiness.md), [format manifest and synthetic fixtures](spec/v0.2.0/fixtures/renpho-v1/manifest.json), [evaluation design](spec/v0.2.0/fixtures/evaluation-plan-v1.json), and [retained probes/results](evidence/v0.2.0/m0-readiness.md#reproducing-the-probes) satisfy M0-A1-A9 as recorded. These establish decisions and bounded mechanics, not AT-01-28 runtime acceptance. Physical Android/actual export MIME remains not run under M2; the first complete applicable manufacturer reference remains an M3 evidence blocker. Only dependent work stops at those gates.

Selected directions and unresolved contracts are recorded in the [decision log](DECISIONS_IMPLEMENTATION.md#v020-m0-decisions-2026-11-13). M1 owns escaping-safe ingress and real capacity proof; M2 owns authenticated and installed-device sharing.

### M1 — Data and imports

**Depends on:** M0's schema, source/identity, registry, and staging decisions.

Deliver complete supported-field preservation, event/observation representation, the versioned adapter, exact unit/time handling, overlap/enrichment/conflict rules, and capacity-safe reviewed commits. Update existing forms/read paths enough to keep the application coherent; the streamlined share experience belongs to M2. Include correction, deletion, export, revision invalidation, and new ownership constraints as entities are introduced. Add events/annotations to lifecycle and private-copy inventories in M1. The existing schema inventory is a hosted build check, not stale-client protection: M1 must refuse incompatible API/client/payload contracts before writes; M2 owns worker continuation/version handling, and M6 owns full cutover rehearsal.

**Exit:** AT-01–08 pass locally with synthetic data, including the 24,000-observation workflow and limits of 1 MiB decoded CSV, 10,000 source rows, and 25,000 numeric observations. No partial committed history, silent exclusions, or model calls. Affected AT-24–27 coverage passes in a disposable environment; generated database types are current. Supported aliases and unresolved semantics are explicit.

M1 contract clarification: use forward extension with no fabricated event backfill; pin current goal/tool capabilities to the existing eight metrics. Version 2 Data writers, source defaults, owned status/discard and exact exports are the M2 integration seam. M1 includes basic event inspection/editing and raw unresolved values; M3 retains the richer event/analysis/reference experience. Explicit review covers invalid cells, conflicts and populated unsupported columns. Retained private baseline values and broad conversation/payload copies are removed on correction/deletion while approved targets/states and accounting remain. The local rehearsal uses an isolated database rather than resetting retained local receipts. See [M1 evidence](evidence/v0.2.0/m1-imports.md) for results and unverified gates.

### M2 — Seamless ingestion

**Depends on:** M1's stable source settings and preview/commit/status contracts; M0 desktop share mechanics. Physical device/MIME evidence and authenticated handoff remain M2 obligations under the procedure in the M0 record.

Deliver one compact preview for file selection and OS sharing, remembered source/timezone choices with reconfirmation on material changes, and clear new/duplicate/conflict/exclusion counts. Implement the bounded local handoff, account-confirmation/sign-in continuity, and truthful cancellation, expiry, uncertain-commit, offline, and update recovery states. Preserve file-picker fallback and zero automatic inference.

**Exit:** AT-09–11 have automated evidence and the physical Android/browser workflow is documented, or an explicit unresolved platform gate remains. Confirm actual RENPHO export → installed app → preview → deliberate commit; synthetic file injection alone does not satisfy AT-09. No file content or identifiers leak into URLs, logs, or public caches.

### M3 — Analysis and references

**Depends on:** M1's stable event, metric, source, and revision contracts; M0 reference investigation. M0 adopted no numeric reference rule from the reviewed general HTML pages. Obtain the complete applicability/threshold/profile evidence named in the M0 record before production classification proof. M2 device evidence is not a prerequisite.

Deliver event detail, discoverable grouped metric views, bounded trends, genuine selected-period summaries and comparisons, and versioned definitions/reference classification. Keep daily medians, equal-day weighting, actual intervals, exclusions, per-metric coverage, and explicit alignment. Separate latest-event values from older latest-per-metric readings and current guidance from historical manufacturer classifications. Write original explanations and charts; review the reuse basis, applicable terms and notices for manufacturer-derived content under REF-07 before including it.

**Exit:** AT-12–15 and affected AT-23–25 pass. Independent expected calculations cover repeated weigh-ins, sparse periods, percentage points, zero denominators, and timezones. UI and compact tool projections share result contracts. Per-metric reference coverage is published, with at least one applicable verified reference through the production path or a blocker that prevents claiming classification ships. Included manufacturer-derived content has recorded reuse review and required notices; unresolved reuse blocks the affected content.

### M4 — Goals and conversation

**Depends on:** M1 ownership/lifecycle and M3 analytical/semantic contracts.

Deliver all eligible numeric goal modes and groups of up to four, direct forms, reviewable conversation proposals, and deterministic group/member progress. Extend bounded tools for definitions, references, event overview, comparisons, and compact multi-metric results. Preserve contextual follow-ups, streaming, cancellation, exact inspection, and content-bound approval. Reuse the existing goal engine and server analytical services.

**Exit:** AT-16–20 pass in offline/control tests, including safety, approval bypass, baseline invalidation, group ownership, missing/stale member evidence, budget exhaustion, and trace expiry. Representative full-panel and grouped-goal tasks fit the existing four-provider-request/six-tool/210-second envelope. Prompt/tool/projection versions are stable enough for M5; existing production evidence does not authorize changed templates.

M0 freezes the comparison rubric and scenario intent. M4 binds final prompts, tools, projections and evidence/result identifiers before paid batches; M5 refreshes provider capabilities/privacy/prices, fixes the candidate/repetition matrix and obtains separate spend approval. M0 design or old technical evidence cannot satisfy live comparison or model activation.

### M5 — Select and verify AI configuration

**Depends on:** Stable M4 prompts/tools and M3 semantics; a separately approved paid-batch matrix and maximum spend before live execution.

Use approximately 16–24 synthetic scenarios through the actual Vulpes user/tool/answer path, with independently checked numbers and a held-out or fresh final subset. Compare current Luna, one supported higher-effort setting where applicable, and one or two similar-tier peers; live baseline-versus-at-least-one-peer evidence is mandatory. Recheck current model identifiers, API features, privacy, effort semantics, and prices at execution time.

Predeclare the rubric, require at least 90% ordinary task completion, and treat critical authorization, approval, privacy, budgeting, fabricated-data, and unsafe-advice failures as disqualifying. Repeat shortlisted configurations on difficult/critical cases at least twice. Report full-task cost including continuations, latency, variation, unknown billing, and human review. A stronger-model experiment is conditional on a specific remaining in-scope failure.

**Exit:** AT-21–22 pass for the selected model/effort/routing policy. Produce versioned JSON and a readable report bound to code, fixtures, prompt, tools, adapters, and price evidence. Verify the exact selected configuration after fixes; consequential configuration changes need approval. Unselected routes stay unavailable. Without authorized live comparison this milestone remains pending; an offline pass cannot substitute.

### M6 — Release and cutover

**Depends on:** All M1–M5 deliverables and applicable evidence; unresolved device/reference gates require explicit disposition before a release claim.

Run the integrated release scenario and regression gates, complete accessibility/device review, and finalize reproducible setup, cutover, backup/recovery, and stale-client procedures. Update current README, agent guidance, version/changelog, operations, and roadmap to the RENPHO direction; preserve accurate historical evidence. Assemble the requirement-to-evidence record for the exact release candidate.

**Exit:** AT-23–28 and all earlier applicable gates are current. The file-picker and supported physical share route, historical analysis, grounded multi-metric conversation, approved groups, and overlapping reimport work together without moving frozen baselines or duplicating records. Deployment/cutover verification occurs only after separate authorization; otherwise label the candidate ready for that step, not deployed or fully released.

## 6. Release risks and early containment

| Risk | Consequence | Containment / decision point |
|---|---|---|
| Capacity expansion across multiple ceilings | A parser succeeds but staging, request transport, SQL, or hosting rejects an ordinary history. | M0 traces all bounds; M1 measures the full 24,000-observation path and transactional latency. Compact metadata before raising limits; no mandatory manual splitting inside the supported envelope. |
| Same-time/source/timezone ambiguity | Legitimate repeats are lost or incompatible histories merge. | M0 defines identity and documented equivalence; M1 adversarial overlap tests. Preserve unresolved conflicts and deliberate source/time mapping. |
| Schema change bypasses lifecycle inventories | Events, remarks, grouped goals, or derived private copies survive deletion or disappear from exports. | Every schema milestone extends ownership/export/deletion/restore coverage; AT-25 is not deferred wholesale to M6. |
| Android receiver differs from desktop emulation | Required share workflow fails at installation, MIME dispatch, cold start, or sign-in. | M0 feasibility and M2 physical proof. Continue independent file-picker work if blocked, but retain the gate and seek an explicit scope disposition before limited release. |
| Local handoff crosses account boundaries | Shared health data uploads to the wrong account or persists beyond the disclosed policy. | M2 account binding, single-consumer claims, expiry-on-read, cleanup, and update/race tests; no upload before authentication/account confirmation. |
| Missing manufacturer semantics/references | Unsupported claims, incorrect units, or clinical-looking labels. | M0 investigation and M3 applicability/coverage audit. Preserve values, mark unresolved meaning, and show reference unavailability rather than inventing ranges. |
| Expanded goal surface exceeds existing safety coverage | A representable index or vendor target becomes an unsafe recommendation. | M4 reviews server-side policy and adversarial target cases; representation validity is not medical endorsement. ## 7. Cutover and completion boundary
